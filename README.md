# IT 开发工作台 · 多端登录会话管理（session-server）

配套前端原型 `E:/工作平台/IT开发工作台/index.html` 的后端会话能力：**多台 PC 同时登录同一账号、登录状态追踪、踢下线、超时失效控制**。

技术栈：Spring Boot 3.0.5（jakarta.*） / JDK 17+ / MyBatis-Plus 3.5.5.x / Oracle 19c，**不使用 Lombok**，时间统一 `java.time.LocalDateTime`。

> 包名根为 `com.appliance.itwb`，如与贵司规范不符，全文全局替换包名即可（IDEA：Refactor → Rename package）。

## 二、接口一览

统一请求头：`Authorization: Bearer {token}`；设备指纹（可选）：`X-Device-Id`。
统一返回：`{"code":0,"success":true,"msg":"success","data":{...},"timestamp":1716000000000}`。

| 方法 | 路径 | 请求 | 响应 data |
|------|------|------|-----------|
| POST | `/api/auth/login` | username, password, deviceType, deviceId, deviceInfo, rememberMe | `LoginResponse`（token、sessionId、userId、expireTime、activeSessions…） |
| POST | `/api/auth/logout` | logoutAll, sessionId(可选) | 登出的会话数 |
| GET | `/api/auth/session/validate` | 查询串 deviceId、slide(默认 true) | `SessionValidateResponse`（valid、expireTime、extended、reason） |
| POST | `/api/auth/session/extend` | sessionId(可选) | `SessionValidateResponse` |
| GET | `/api/auth/sessions` | 查询串 pageNum、pageSize、deviceType、keyword | `SessionPageResult<SessionVO>`（含 `current` 标记是否为当前终端） |
| POST | `/api/auth/sessions/kick` | scope(CURRENT_USER/SAME_DEVICE/ALL_DEVICES)、sessionId、deviceType、remark | 被踢掉的会话数 |

## 三、三个必须知道的设计点

### 1) Oracle 与 MySQL 在本设计中的 3 个关键差异

| # | 差异 | 本项目中的处理 |
|---|------|---------------|
| 1 | **唯一索引对 NULL 的处理不同**：Oracle/MySQL 的唯一索引**允许多个 NULL 行**（MySQL 也是允许多个 NULL，但 Oracle 的 NULL 完全不参与唯一性判定，语义上更容易被误解为"唯一"），因此 `SESSION_ID` 若可为 NULL，"UNIQUE"形同虚设。另外 Oracle 的 VARCHAR2 是**按字节**存储，中文易超 4000 字节上限（MySQL 5.7+ 的 utf8mb4 行内上限也各不相同）。 | `SESSION_ID` 显式 `NOT NULL` + 独立唯一索引 `UK_SYS_USER_SESSION_SESSION_ID`；长文本字段用 `CLOB`（USER_AGENT）而不是加大 VARCHAR；`DEVICE_INFO` 控制在 500 字符内不会越界。 |
| 2 | **ROWNUM 分页必须嵌套子查询**：ROWNUM 在排序完成之前就已分配，直接 `ORDER BY ... WHERE ROWNUM<=N` 会先取后排，翻页必错。Oracle 也没有 `LIMIT`。 | MyBatis-Plus 的 `PaginationInnerInterceptor(DbType.ORACLE)` 自动生成三层嵌套（内层过滤+排序、中层 `ROWNUM<=?`、外层 `RN>?`）。业务代码写 `mapper.selectPage(page, wrapper)` 即可，与 MySQL 写法一致。 |
| 3 | **无自增列机制的历史包袱与时间精度**：Oracle 12c 前没有 `IDENTITY`，得用"序列 + 触发器"；Oracle 的 `DATE` 只有秒级精度，没有 MySQL 的 `datetime(3)` 毫秒。 | 12c+ 用 `NUMBER GENERATED BY DEFAULT AS IDENTITY`（11g 的替换脚本在 SQL 文件末尾）；所有时间列用 `TIMESTAMP(6)`，对应 Java 的 `LocalDateTime`，毫秒不丢。 |

**额外补充（第 4 点，容易踩）**：Oracle 默认**读已提交**隔离级别，且**读一致性快照**让"先 SELECT 后 UPDATE"产生覆盖写的问题——所以本工程所有状态变更都是 `UPDATE ... WHERE <条件>` 靠**影响行数**判定，没有一处先查后改。

### 2) 多端并存 vs 单点登录：推荐默认值

**推荐默认 `itwb.session.multi-login-enabled: true`（多端并存）**，理由：

1. 用户的典型场景是 **IT 开发经理同时开 2~3 台电脑查 ERP**（前台接单机 + 后台分析机 + 出差用的笔记本）。一旦默认单点，用户每次换机器都要被踢，体验成本远高于"多留几个会话行"。
2. 多端并存 + **单用户最大会话数上限（默认 5）** 已经堵住了"会话无限堆积"的风险，超限时按 `LAST_ACTIVE_TIME` 淘汰最旧的一台，行为可预期。
3. 需要"禁止同时在线"的场景（如涉密、财务审批）由管理员在后台把开关调成 `false` 即可，**同一份代码两种模式**，不需要两套逻辑。

关掉开关后的语义是**按同设备类型（DEVICE_TYPE）踢旧**，而不是"踢掉全部终端"：
同一台 PC 再登录一次，旧 PC 会话被顶掉；手机端不受影响。这样最符合"我不想在同一台机器上开两个窗口"的直觉，也避免员工手机上操作被电脑端登录挤掉。

| **`TokenProperties.secret`** | 生产环境必须配（建议环境变量 `ITWB_TOKEN_SECRET`）。留空会在启动时自动生成随机盐并打 WARN，**每次重启都会让所有已登录会话失效**。 |
| **Oracle 版本** | 11g 用户请按 SQL 文件末尾"11g 兼容说明"改为序列 + 触发器，并把实体 `@TableId` 策略改为 `IdType.INPUT`。 |
| **IDENTITY 主键** | 主键由应用层 `ItwbIdentifierGenerator` 生成（MP 任意 `IdType` 都会把主键列显式写进 INSERT，实体 id 为 null 时写 `ID=NULL` 会触发 ORA-01400，故不能用 `INPUT`）。数值型 `Long` 实体用 `IdType.ASSIGN_ID`（雪花 Long），字符串型 `String`（底层列仍是 NUMBER）实体用 `IdType.ASSIGN_UUID`（雪花数字字符串）。库里没有 `CREATE SEQUENCE`，故不用 `AUTO`（会走 KeyGenerator 报 ORA-02289）。11g 用"序列+触发器"时把策略改回 `IdType.INPUT` 即可。业务逻辑不读 `id`。 |

| **`@EnableScheduling`** | 若主工程已有，删掉本模块的启动类即可；没有则保留。 |
| **网关/反向代理** | 若部署在 Nginx 后，务必在 `resolveClientIp()` 之前确认可信代理头（X-Forwarded-For 可伪造），必要时只信任最后一级代理写入的值。 |

## 四、权限边界与性能取舍

### 权限边界（会话接口只能操作自己的会话）

会话管理接口的硬约束：**任何人只能操作自己名下的会话**。代码落了三层防线：

1. **Controller**：userId 只从服务端会话上下文（过滤器写入的请求属性）取，不接收前端传参；
   logout 允许显式传自己的 sessionId，但仅此而已。
2. **Service**：`kick()` / `logout()` 拿到目标会话后立刻校验归属，不匹配直接拒绝并打 WARN；
   `kickByDeviceType` / `kickAllByUserId` 的 userId 参数本身就是调用方身份，语义上即归属约束。
3. **SQL**：`kickBySessionId` 的 WHERE 里带 `USER_ID = #{operatorId}`，
   即使将来有人在 Service 之外新增调用入口，数据库这一层也只会返回 0 行，而不是踢掉别人的会话。

### 校验接口是否写库

**不写。** `validate()` 在 `slide=false` 与`slide=true`（且剩余有效期 ≥ 续期阈值）两种情况下都是
一次按哈希的等值查询、零写操作；`slide=true` 且临近过期时才执行一次原子续期 UPDATE；
已过期的会话**刻意不改 STATUS**（否则僵尸会话会在每次轮询里反复写库），状态回收统一由
10 分钟一次的清理任务负责。若每请求都写 last_active_time，万台并发就是上万次 UPDATE/秒。

## 五、核心并发与性能取舍

- **登录并发**：`/api/auth/login` 上同一账号多线程同时登录时，靠 `UPDATE ... WHERE SESSION_ID=? AND STATUS='ACTIVE'` 的**条件更新 + 影响行数**判定，不做"先查后改"，避免互相踢错。会话数超限淘汰是"尽力收敛"，允许极端并发下短暂超 1~2 个，随后被下一轮淘汰或自然过期。
- **校验写库频率**：校验接口**默认不写库**。只有"剩余有效期 < `extend-threshold`（默认 5 分钟）"时才执行一次原子 `UPDATE` 把 `LAST_ACTIVE_TIME` 与 `EXPIRE_TIME` 一起前移；其余请求只做一次按哈希的等值查询。若每请求都写库，万台并发就是上万次 UPDATE/秒，Oracle 会先扛不住。
- **滑动续期上限**：新过期时间 = `LEAST(现在 + 最大空闲, 登录时间 + 绝对上限)`。即使每天点一次，8 小时后仍然强制失效。
- **`LAST_ACTIVE_TIME` 语义**：表示"最后一次确认活跃（续期）"的时间，用于淘汰排序与统计；**是否在线由 `EXPIRE_TIME` 决定**，`STATUS` 只是逻辑状态，两者都要判。

## 六、Spring Security 衔接（SecurityConfig）

`session/config/SecurityConfig.java` 已把 `TokenAuthenticationFilter` 接入 Spring Security 6
（`spring-boot-starter-security`，Boot 3.0.5 托管 Security 6.0.8，pom 无需写版本号）。

### 请求处理顺序

```
请求 → SecurityFilterChain
        ├─ TokenAuthenticationFilter（addFilterBefore，位于授权判断之前）
        │    ├─ 白名单路径 → 直接放行（不设身份）
        │    ├─ 校验失败   → 直接写 401 Result JSON，请求终止
        │    └─ 校验成功   → 写请求属性 + SecurityContext（principal=userId，ROLE_USER）
        ├─ authorizeHttpRequests（白名单 permitAll，其余 authenticated）
        └─ Controller（请求属性照旧直读，老代码零改动）
```

### 三个必须知道的机制

1. **容器级注册已禁用**：过滤器标了 `@Component`，Boot 会把它同时注册到 Servlet 容器链；
   `SecurityConfig#tokenFilterRegistration` 用 `setEnabled(false)` 关掉容器级注册，
   只保留 Security 链内一份，避免 OncePerRequestFilter 的 ALREADY_FILTERED 标记造成
   "第二次调用被静默跳过"的隐性行为。
2. **SecurityContext 用完即清**：STATELESS 模式没有 HTTP 会话兜底，过滤器在
   `finally` 里 `SecurityContextHolder.clearContext()`——容器线程复用时若不清空，
   上一个请求的身份会串给下一个请求，这是无状态过滤器最隐蔽的事故源。
3. **白名单同源**：Security 的 `permitAll` 与过滤器的放行路径共用 `itwb.session.skip-urls`
   （`SessionProperties`），改一处两边同时生效，不存在"过滤器放行了、Security 又拦住"的不一致。
   ⚠️ **需要身份的接口绝不能进白名单**——例如把 `/api/auth/logout` 放进去后过滤器跳过校验，
   userId 属性为空，Service 层归属校验会直接拒绝，表现为"登出永远返回 0 行"且无任何报错。
   （本版本已把 logout 移出默认白名单，这正是修复的一个真实缺陷。）

### 401/403 输出

与业务接口同构的 `Result` JSON：令牌无效/缺失由过滤器直接写 401；
`authenticationEntryPoint`（401）与 `accessDeniedHandler`（403）只作兜底。

### CORS

允许来源来自 `itwb.session.cors-allowed-origins`（见 `SessionProperties`，默认含
`http://172.16.132.64:8088` + `http://127.0.0.1:8088` + `http://localhost:8088` 三类 8088 来源）。
允许头含 `Authorization` / `Content-Type` / `X-Device-Id`，预检缓存 1 小时，预检（OPTIONS）放行。

**为什么是具体来源而非 `*`**：带 Bearer 令牌透传时放 `*` 等于裸奔；Phase C 已收紧。
**为什么必须覆盖本地来源**：浏览器以 127.0.0.1 / localhost / 其他 IP 打开 8088 静态服务器时，
请求头里的 `Origin` 必须命中白名单，否则预检 403 且无 `Access-Control-Allow-Origin`，
前端带令牌的实时数据请求被浏览器拦截、无法从 18077 拉取。生产部署按真实前端地址覆盖该配置即可，
不要改回 `*`。

### 依赖变化

pom 新增 `spring-boot-starter-security`（唯一新增依赖）。引入后 Boot 的默认安全配置
自动让位于 `SecurityConfig` 里的自定义过滤链，无需额外开关。
